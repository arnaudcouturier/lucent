# Stable content candidate 2026.10.31

2026.10.30 on **OptiScaler-FFXIV v0.5.1** (tag `ffxiv-2026.10.31b-d9b62110`, commit `396823cb`, published). Everything else (Automatic ReShade scene depth on by default, the Alive 4K removal, the ReShade settings, the Graphics-step choices, Streamline, the runtimes, the tiers) is 2026.10.30 unchanged. It is `stable` with `minAppVersion` **1.0.2**: nothing in v0.5.1 needs app code, so it does not wait for an app release. The maintainer played v0.5.0 in game on 2026-10-31 and made it Latest, then published v0.5.1 as Latest; v0.5.1 only changes the `ProbeInterval` default that session tried, so the content goes straight to Stable with no Beta stage. One content version carries the three fork releases, so its changelog repeats the lines a player on 2026.10.27, .28 or .29 has already seen.

## What the fork changed

- **Package.** `OptiScaler-FFXIV-ffxiv-2026.10.31b-d9b62110.zip`, 132,969,401 bytes, SHA-256 `ac19e9f59efe8f0c3d0a404c9289fef11a204058e987739c7fe8f34d31b12974`: it matches GitHub’s digest and every line of the package’s own `SHA256SUMS.txt` (`prepare-fork-candidate` checks both). It holds 24 entries: the 23 of v0.3.0 plus `settings-schema.json` at the root. Lucent does not deploy that file. `prepare-fork-candidate` reads it from the zip and checks the recipe’s ini writes against it: a key Lucent writes must be in the fork’s ini and must not be retired or renamed, and its value must be one the key takes, or the candidate is refused. It also reports which keys apply live and which the fork’s ini gained or dropped. The release also puts a sidecar `OptiScaler-FFXIV-ffxiv-2026.10.31b-d9b62110-settings-schema.json` beside the zip; it is not inside the zip, and no fork script uploads it. The tag-first build check is stricter: the embedded `git describe` string must be `<tag>-0-g<sha>`, a `-dirty` tree is refused, and the tag must resolve to the commit the DLL was built from. Against v0.3.0, seven files changed and one was added, and nothing was removed: `winmm.dll` (30,032,384 bytes, SHA-256 `249017f46d5a79ce29172207572c1fa0cb0ee297f7a65b727d47085e9e8fbd2c`), `nvngx.dll_dlssnr.dll` (151,552 bytes), `OptiScaler.ini` (146,658 bytes, SHA-256 `6435b17123286f60989d18dc9f987c43a812070fc6bc54056885bb221921b6ae`), `NOTICE.txt`, `INSTALL.txt`, `Licenses/ATTRIBUTION.md` and `SHA256SUMS.txt` changed, and `settings-schema.json` was added. The recipe carries the zip, `winmm.dll` and `OptiScaler.ini` SHA-256 values.
- **The ini.** It holds 537 keys, against 503 at v0.4.0 and 483 at v0.3.0. 57 keys were added and 3 removed since v0.3.0 (the removals are listed below); the added ones are all at `auto`, which is the fork’s own default:

v0.5.1 is the same package as v0.5.0: the same 24 entries and the same 537 keys, with no value changed. It changes the fork’s built-in default for `[HudLess] ProbeInterval` to 8; the ini still ships `auto`, and its comment says "Default (auto) is 8". The `ui_free` comment now says the micro-stutter seen while the coverage guard was tripped was removed by the default probe interval of 8 in the one play session it was tried (2026-10-31, DLSS-G preset C; at 1 it came back), and that recomposition with `[DLSSG] RenderPreset = auto` is the safe choice.

- **What it does to a saved ini.** Three keys were removed: `[Companion] HudReplacement` and `HudInterpolation`, whose feature the fork deleted, and `[FFXIV] AutomaticReShadeMotionScale`, which is retired in the schema; the per-axis motion-vector scaling it could turn off is now always on. Every key Lucent writes or reads still exists, so no choice, override or update key changes meaning. Against the maintainer’s saved ini the merge reports 80 carried values and 1 lost: `[Companion] HudInterpolation = true` has no key left to land in. `iniOverrides` gains `[HDR] LegacyComposition = false`, the continuous composition of world and interface light, which only matters with Scene HDR (`[HDR] Mode = 1`); `UiExpansion` stays `auto`.
- **Tried in game.** One played session on 2026-10-30 ran the frame generation recorder, an earlier version of the tick probe and the HUD-less log counters. The fork’s `ui_free` comment cites one played session on 2026-10-31 with DLSS-G preset C, where the default probe interval of 8 removed the micro-stutter and `ProbeInterval = 1` brought it back. Everything else in v0.4.0 and v0.5.0 is unit-tested or benchmark-only, and the HDR composition has not been tried on an HDR display.

## What it means for Lucent

- **A new first-install choice: the frame rate governor.** The Graphics step gets a choice in the Neural Rendering card, outside the Advanced hints group, with Off (default) and Hold frame rate (Experimental). It writes `[DlssNr] Governor` and leaves `GovernorTargetFps` at 0, which is auto. It is content only, so no app release is needed. An existing setup gets the key at `auto`, which the fork reads as off, through `addMissingKeys`; a Reset offers the choice, and the changelog says so.
- **UI-free stays Experimental, with the fork’s default probe interval.** Its description says frame generation works on the scene alone and the interface is pasted back at the real frame rate, that its micro-stutter in motion was removed by the fork’s default probe interval in the one play session it was tried (DLSS-G preset C), and that Recomposition with DLSS-G preset Auto stays the recommended setup. A player who picked UI-free keeps it.
- **Nothing else new is offered.** Nameplates, contact shadows, the live output switch, the foveated profile, the Neural Rendering hotkeys, the FSR frame ID, the bridge flush, the probes and the diagnostics stay at the fork’s off default and have no choice.
- **Existing players.** `OptiScaler.ini` keeps `addMissingKeys`, so an update adds the new keys at the baseline’s values, `[HDR] LegacyComposition` at `false` and `[DlssNr] Governor` at `auto`, and changes nothing else. The `optiscalerUpdateKeys` entry from 2026.10.29 stays, so a player who goes straight to 2026.10.31 still gets `AutomaticReShadeDepth` switched on while the key reads `auto`. The dead `[Companion]` and `AutomaticReShadeMotionScale` lines stay in a player’s file and are ignored: Lucent never deletes a key, and only OptiScaler’s own Save Settings would drop them. The new `generatedFolders` are removed by Uninstall alone, and only when the path did not exist at the install or update that recorded it, so a folder the player made survives; a path Lucent created goes, kept recordings and capture runs included.
