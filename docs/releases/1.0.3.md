# Lucent 1.0.3

- **Settings has a Storage card that clears Lucent's cache and its backup copies.** The Cache row shows what Lucent has downloaded and kept, and Clear… removes it; Lucent downloads what it needs again the next time you install, update, change version or repair. The Backups row, which moved here from Game folder, shows the copies of the files Lucent replaced. Clear… lists each folder and what it is: the copy from your install and the ones a Reset set aside start ticked, because Lucent keeps its own backups of the same files. The originals an Uninstall left out start unticked and warn that they can't be put back, since those are the only copies. Lucent's own backups, which Uninstall restores from, are never touched, and an Uninstall that leaves your replaced files out (the vanilla choice) writes their copies again from those backups if you had cleared them. Neither clears while Lucent is busy or needs recovery, and XIV can be running.
- **Settings has an After a game patch switch, off by default.** OptiScaler-FFXIV finds the game's code addresses itself, and after a patch the features that read the game's code stay off unless this is on and every address is found. The switch sets that one key in `OptiScaler.ini` and nothing else, and a Reset keeps it. It takes effect the next time XIV starts, it is disabled while XIV runs, and it needs content 2026.10.30 or newer, which is published. It is experimental: the fork has not tried it on a real game patch.
- **Nothing else changes.** Every other screen and the setup Lucent writes are as they were in 1.0.2.

## Validation — 2026-10-26

- TypeScript: `npm run typecheck` clean and 1336 tests passed. `cargo check --manifest-path src-tauri/Cargo.toml --locked` clean on 1.0.3 through the debug build; the Rust source is unchanged since 1.0.2, so its tests were not rerun here (the release workflow runs them).
- Clear storage: 29 core tests and 3 screen tests, including the case the pre-release review found: Clear backups removes a live deployment's install copy, which a later vanilla Uninstall then needed as the only readable copy of the files it leaves out. A vanilla Uninstall now writes any missing copy again from the journal's backups, checked against their hashes, before it changes anything, leaves a copy that is there alone, and stops with the game folder untouched when a journal backup is missing or a copy fails its check. Sizes are summed file by file; the cache counts only Lucent's hash-named files and `.tmp` downloads and leaves any other file; a live deployment's copy, a Reset's, the originals a vanilla Uninstall kept, those of a game folder that is gone and a stranger's folder are told apart, and none of a deployment's copies is offered as redundant while a record can't be read. Clearing removes only the named folders and then `Backups` itself when it is empty, leaves a stray file alone, and never touches the journal's backups, the records or the game folder; names with `..`, empty parts or stream and wildcard characters never reach the port, which the tests show with a listing that lies and a size check that finds every planted name. It refuses with its reason when another process holds the lease, while Lucent is busy and while a change needs recovering. Repair and Reset download again after the cache is cleared, and Uninstall still puts a player's files back after both folders are cleared.
- After a game patch: 21 core tests and 5 screen tests. The key reads on for `true` and off for `auto`, `false` or a missing line, with a reason when the ini is missing, unreadable, locked or predates the key. Turning it on writes `true` to that one line and leaves every other byte of the file, including its line endings; off writes `false`; both go through the journal, so Uninstall leaves the game folder vanilla. A Reset, a new graphics card's rewrite of the baseline, a content update and the Repair of a missing ini keep the value; it refuses while XIV runs, while another process holds the lease and on a locked ini; and on a game folder that needs administrator access it asks once and sets the switch after the elevated restart.
- Mutation check on the new code: 40 mutants, each a one-line change (a vanilla Uninstall that does not write the copies again, writes over one that is there, ignores a missing journal backup, skips the hash check or keeps a bad copy, a name with `..` or a stream character accepted, any cache file removed, the kept originals ticked, a copy classified wrongly, Clear allowed during recovery or while busy or without the lease, the Reset or Repair forgetting the switch, the switch written inverted or as `auto`, not journaled, written to a locked ini or one without the key, the elevated request refused or not replayed, a Clear button left on while busy and the switch left on while XIV runs). The first run left six alive; the tests were strengthened (a size check that finds planted names, a core test of the administrator path, of the lease and of the elevated resume, and a button match that cannot run across buttons), and all 40 are killed.
- On the real exe (the 1.0.3 debug build, 2026-10-26, isolated data and a dummy game folder holding the player's own `ReShade.ini`, `winmm.dll` and a preset, content served from the 2026.10.30 candidate; XIV closed): a first install on Stable content 2026.10.30 over that setup was Healthy. Settings showed the switch off and the Storage card with the cache at 156 files and 543.4 MB and one backup folder; turning the switch on changed one line of the 2,482-line `OptiScaler.ini` (`FfxivUnknownBuildHooks=auto` to `true`, line endings kept) and the record and journal noted it; a Reset kept `true`. Clear backups listed the install copy and the Reset copy, both ticked; with the install copy unticked only the Reset copy went (3 files, 120.6 KB); clearing the rest removed `Backups` and its row. Clear cache removed all 156 files and the row read Empty. With the cache empty, deleting `winmm.dll` and pressing Repair downloaded the one file it needed and was Healthy again. Uninstall (put my earlier files back) then left the game folder with exactly its five original files and the player's `ReShade.ini`, `winmm.dll` and preset as they were. A second real run on the build with the review's fix: after Clear backups removed the install copy, an Uninstall with "Restore the game to vanilla" wrote the two copies again, byte for byte the originals, left the game folder vanilla apart from the player's own preset, and its notice named the folder. The dev browser's Settings showed the cards and the confirm dialogs, and the answer scrolls into view.
