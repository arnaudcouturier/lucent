# Lucent — Design Decisions

Settled in a design grilling session on 2026-10-12. Each section is a decision; "Deferred" lists what is intentionally still open.

## Product

- **Lucent** is a public, open-source (MIT for our own code) Windows manager for FFXIV that deploys OptiScaler with DLSS 5 Neural Rendering, ReShade (add-on build), shaders and presets.
- It is a **manager, not a one-shot installer**: it stays useful after setup (repair after patches, updates, rollback, Reset, clean uninstall). It does not manage the config files once they are deployed (see Scope reset).
- **Positioning** (settled 2026-10-13): Lucent is presented as a manager for XIV graphics mods. DLSS 5 (OptiScaler) and ReShade are its two features, not its identity, so the site, README and app copy can take on more features without a rebrand. The Mods section (Starter set, settled 2026-10-16) is the first addition; it is not a deployment and not a Feature in the glossary's sense.
- **Form:** one portable GUI `.exe`. No `.bat` / `.ps1`.
- **Stack:** Tauri 2 + React + TypeScript. Rust side stays thin: file ops, hashing, archive extraction, registry, GPU detection. Chosen because the project is vibe-coded and TS/React gives the highest aesthetic ceiling; Electron rejected (portable build unpacks on every launch), WinUI/WPF rejected (single-file pain, lower ceiling).
- On first run it offers to install itself to `%LOCALAPPDATA%\Lucent` with a Start Menu shortcut and a per-user Settings → Apps entry (no admin). The offer is an **"Add Lucent to the Start menu"** checkbox on the Profile step, on by default.
- Windows 10 22H2 and 11, x64 only. English only. No telemetry.
- Name: **Lucent**. Use "XIV" rather than "FFXIV"/"Final Fantasy" in branding. No Square Enix logos, art or fonts.

## Scope reset

Settled in a design grilling session on 2026-10-14. It supersedes the parts of earlier decisions that had Lucent manage config files after deployment; the sections below are rewritten to match.

- **Lucent deploys a tested baseline and then keeps out of the configs.** Options are offered once, on the first-install choices screen, and written into the config files. From then on `OptiScaler.ini`, `ReShade.ini` and the other config files belong to the player, who tunes them in OptiScaler's and ReShade's overlays.
- **What stays after deployment**: the health check and Repair for core files (DLLs, runtimes, shaders; shipped presets only have to exist, as before), updates, pin, skip and rollback, **Reset**, Enabled, Uninstall, App uninstall, Keys, Logs, Launch XIV and the XIVLauncher add-on.
- **What goes**: the performance profile, Frame generation, HDR and Preset controls on Home; user changes, reset keys and the three-way merge; Custom; screen-derived settings rewritten after deployment; changing settings while XIV runs.
- **Health check**: config files only have to exist and be readable, which 0.1.1 already does. A missing one is drift and Repair writes it from the baseline and the stored first-install choices; their contents are never compared.
- **Repair vs Reset**: Repair (the status card on drift, and the XIVLauncher add-on when the game closes) puts back only the drifted files, so it never undoes a player's tuning. **Reset setup…** in Settings is the deliberate way back: it shows the first-install choices again, prefilled with the stored ones, backs up the current config files, then rewrites everything. It is also the only way to change profile, frame generation or HDR later. A tier switch is a Reset with the new tier's options.
- **Config update rules**: each content version gives each config file one rule: **keep** (default), **add missing keys** (for a new OptiScaler build's new keys; keys already on disk keep the player's values) or **replace** (backed up first, written from the new baseline and the stored first-install choices). The changelog announces add missing keys and replace. It needs no record of what Lucent last wrote. (2026-10-24: a file may also carry `setKeys`, see "Set keys on update" under Deployment engine.)
- **Code after 0.1.1**: what computes values at deploy time stays (frame generation options per tier, profile values, reading XIV's screen); what manages configs after deployment is removed. Check for updates' status line and key names for the player's keyboard layout don't manage configs and stay.
- **0.1.1 deployments**: files on disk are left as they are and the record of what Lucent last wrote is dropped. Lucent infers the stored first-install choices for Reset: the recorded profile (the old two-pass Fidelity becomes Ultra), frame generation Off, HDR Off.
- **Content**: the Beta candidate keeps frame generation, HDR and the four profiles, now offered on the first-install choices screen; it is published once an app with that screen ships. Its 4090 QA checklist checks each choice from a fresh install or Reset.
- Rejected: a Reset that silently re-applies the stored choices (no way to change them without uninstalling); a single Restore that also handles drift (a game patch would wipe the player's tuning); a whole-file replace on every update (resets the selected preset and keybinds every time).

## GPU tiers

Tiers are data in the manifest, not code. Lucent always picks the discrete GPU (the dev machine has an RTX 4090 plus an AMD iGPU) and offers a tier switch when the GPU changes.

| Tier | Payload | Status at launch |
|---|---|---|
| RTX 50 | NVIDIA original `nvngx_dlssnr.dll` runtime + full stack | Community-verified (cannot be tested on dev machine) |
| RTX 20/30/40 | ShortFuse compatibility runtime + full stack | Stable (tested on 4090; RTX 20 and 30 untested) |
| Radeon | OptiScaler FSR upscaling + FSR frame gen + ReShade, no Neural Rendering | Experimental until a real Radeon owner confirms |
| Anything else | ReShade + presets only | Stable |

Untested tiers stay Experimental (labelled in the UI) until testers confirm them.

## First-run flow

1. **Scan**: game folder, GPU, launcher, existing mods.
   - Stable stays the default. When beta content is available for the graphics card, Scan offers an explicit Beta channel switch before the first deployment and refreshes the file list when it changes. A tier with no content on the selected channel says so and cannot continue.
   - Game detection order: XIVLauncher `%APPDATA%\XIVLauncher\launcherConfigV3.json` (`GamePath`), Steam libraries (app 39210), Square Enix launcher uninstall registry entry, default paths, manual picker validated by `game\ffxiv_dx11.exe`.
   - Existing mods detected: GPosingway, leftover GShade files, regular ReShade (`dxgi.dll` etc.), other OptiScaler installs, swapped DLSS DLLs.
   - Scan is **the only place that lists what the deployment does to files already there** (settled 2026-10-13): every file it backs up, then replaces or removes, where the readable copy goes, and the presets it keeps. One "Existing setup" row with a folder tree behind "Show files"; nothing repeats it on Review.
2. **Profile**: the first-install choices, so Review only reviews (settled 2026-10-13, widened by the scope reset on 2026-10-14). This is the only place they are offered, besides Reset and tier switch, which show the same step prefilled.
   - The performance profile (Ultra / Fidelity / Balanced / Performance, preselected and tagged "Recommended for your RTX 4070"), each showing its features read-only: Neural Rendering passes, upscaling quality at the player's resolution, spatial compression and residual frame generation. Passes come with the profile and aren't a choice of their own.
   - Frame generation (Off · 2× … 6× · Dynamic, filtered to the card), with Experimental tags on multipliers that need an unlock: picking one is the opt-in.
   - HDR (Off · HDR · Scene HDR), only on an HDR monitor.
   - "Include ReShade" (on by default; not offered when the tier requires it) and "Add Lucent to the Start menu" (on by default; not offered once Lucent is in the Start menu).
   - A tier without profiles shows the step as **Options**; it's skipped when nothing is left to choose.
3. **Review**: read only. Files backed up / added, download size, and a summary of the choices.
4. **Install**, then a done screen that teaches the in-game keys, read from the configs it just deployed (settled 2026-10-13: hardcoded Insert/Home had drifted from the content's Shift+F2), and links to the guide on the site.
   - Install shows four stages: Downloading, Backing up (the readable backup, only when there is one), Applying, Checking. Progress reaches the UI at most ten times a second and the bar, figures and crystal ease between reports.

- All presets are always installed; **no preset is active** by default.
- Install is blocked while `ffxiv_dx11.exe` is running.
- Admin rights are requested only when the game folder needs them (e.g. Square Enix launcher installs under Program Files).
- No preset previews/screenshots in the app.

## Main screen

- **Layout** (settled 2026-10-13; the ⋯ menu hid features too important to tuck away): the rail keeps the crystal and navigates between six sections, **Home**, **Keys**, **Versions**, **Logs**, **Settings** and **Help** (a seventh, **Mods**, sits between Versions and Logs; see Starter set), with a dot on a section that needs the player (caution on Home for drift or a missing folder, accent on Versions for a content update, accent on Settings for an app update — settled 2026-10-15, moved there from Versions since Versions never showed or actioned an app update). The graphics card and the setup Lucent applies for it sit in a small card at the rail's foot; that is where the tier badge appears.
  - **Home**: the status card, **Launch XIV** and Enabled. No setting controls (scope reset, 2026-10-14).
  - **Keys**: every in-game key, read from the game folder's configs each time the section opens.
  - **Versions**: content, game version and channel, then roll back or apply a version.
  - **Logs**: a terminal that tails Lucent's activity log and the logs the deployed tools write in the game folder.
  - **Settings**: how Launch starts XIV, Beta channel, XIVLauncher auto-repair, the game folder (with Scan), and a danger zone with **Reset setup…** and Uninstall. Reset's confirmation says the config files go back to the tested setup and where the current ones are backed up.
  - **Help**: the guide, Report a bug, Copy diagnostics, then Credits.
  - **Mods** (settled 2026-10-16, built 2026-10-17): a seventh section, between Versions and Logs, for the Starter set of Dalamud plugins and Penumbra mods. It needs no deployment, so the first-run steps carry a **Mods** entry under them as well, and its header then offers **Back to setup**; only an install in progress keeps it away. See Starter set (Mods).
- **Launch XIV** (settled 2026-10-13, replacing "no Launch game button"): starts XIV the way the player does, without closing Lucent. XIVLauncher when it's installed and its readable config points to this game folder; Steam for a Steam copy; otherwise the Square Enix launcher in `boot`. The label below Launch follows the selected launcher. When several apply, an arrow beside Launch opens the choice; Settings also offers it, and the choice is remembered. While XIV runs the button reads "In game".
- **Status card** with one contextual action: healthy or Disabled → a quiet **Scan** (a full hash check now, settled 2026-10-13, so a problem shows without reopening Lucent; also under Settings → Game folder); drift → **Repair**; update available → **Update**. The changelog shows **inline in the status card** with **Skip** and **Update** buttons (no modal).
- **An update never hides outright behind drift or the running game** (settled 2026-10-15, Home only — Review and Versions keep the one card above): if drift or "XIV is running" is the primary card, any pending app or content update still shows, each as its own slim row below the primary card — just the version and an **Update** button, no changelog. Still fully suppressed while something is busy, the game folder is missing, or a tier switch is pending, since acting on anything else isn't safe yet. Two pending updates (app and content) get two independent rows, never a combined one. Settings' **Check for updates** card gained its own **Update**/**Skip** buttons, for an app update only — a content update is still actioned exclusively at Versions, which already lists every version with its own Apply/Roll back.
- **No performance profile, Frame generation, HDR or Preset control** (scope reset, 2026-10-14, replacing the segmented controls and the preset picker settled on 2026-10-13 and 2026-10-14). They are first-install choices; afterwards the overlays are where players change things, and Reset is how they choose again.
- **Master switch labelled "Enabled"**. Turning it off leaves the deployment **Disabled**: files present but inactive. The state persists through repair, update and Reset, and a health check on a disabled deployment expects the disabled state. Not called "Vanilla mode", because "vanilla" means a game folder with no deployment (and is also an Alive preset name). Locked while XIV runs.
- No separate DLSS 5 toggle (OptiScaler's overlay has one).
- **Logs** (settled 2026-10-13): Lucent keeps an **activity log**, `%LOCALAPPDATA%\Lucent\lucent.log`: a line for what Scan found, each command and its outcome, every error and notice the window shows, and every file it writes, renames or removes in the game folder. It is a file, not memory, so the window, a relaunch with administrator access and XIVLauncher's headless runs all add to one account, and a first install can be read afterwards. Past 512 KB it is cut back to its last 2,000 lines when Lucent opens. It never leaves the machine (no telemetry) and is not part of Copy diagnostics.
  - The section shows it as a terminal: Geist Mono on the darkest surface, a timestamp per second rather than per line, file lines dimmed, a finished command in the accent, warnings and errors in the caution colours (no new colour), and a caret at the end. It follows new lines until the player scrolls up, then offers **Latest**. **Copy** puts the shown lines on the clipboard.
  - The logs the deployed tools write (`OptiScaler.log`, `ReShade.log`: the content version's generated files that end in `.log`) sit beside it as tabs, read from the game folder every second while the section is open.

## Frame generation, frame cap, HDR and profiles

Settled in a design grilling session on 2026-10-13. Since the scope reset on 2026-10-14, frame generation, HDR and the profile are first-install choices written once, not controls on Home.

- **Frame generation** is a first-install choice: **Off · 2× · 3× · 4× · 5× · 6× · Dynamic**, filtered to what the player's card can run. It is separate from the profile.
  - The options are manifest data per tier, filtered by GPU model, since RTX 30 and RTX 40 share a tier but not an unlock. The planned matrix is RTX 40: 2× native, 3×–6× through the fork's built-in `AdaMfgUnlock`, Dynamic only once it is verified on the RTX 4090; RTX 50: all multipliers natively; RTX 20, RTX 30 and Radeon: 2× through FSR frame generation, then XeFG MFG where the runtime and license allow it. The 2026.10.15 RTX 30/40 Beta candidate is narrower: RTX 30 offers Off and experimental 2× FSR only. RTX 30 XeFG MFG is deferred pending Intel license clearance; its HDR fallback uses XeFG at 2× with every MFG unlock and dynamic setting disabled. RTX 40 options are separately gated by the 4090 QA checklist.
  - Multipliers that need an unlock carry a yellow **Experimental** tag. No confirmation dialog.
  - One line under the control says what the choice means at the frame cap: "XIV renders up to 56 fps, shown at 224 on your 240 Hz screen", or "Aims for 224 fps on your 240 Hz screen" for Dynamic. Every supported multiplier stays offered, even one that renders XIV slowly; the line makes the trade-off visible.
  - Default on the first-install choices: 2× on screens of 120 Hz and up, Off below. A 0.1.1 deployment keeps its config as it is, and Reset offers Off.
  - A multiplier changed in OptiScaler's overlay is the player's business; Lucent doesn't read it back.
  - Rejected: building frame generation into the profiles; sdli1995's `dlssg_sm86` runtime for RTX 20/30 (an external component nobody here can test, with Dynamic in only one variant).
- **Frame cap**: `[Framerate] FramerateLimit`, `[DLSSG] FramerateTargetDMFG` and `[XeFG] DynamicTargetFPS` are all `floor(R − R²/3600)` for refresh rate R: 138 at 144 Hz, 224 at 240 Hz. That is the cap Reflex applies itself with G-Sync or FreeSync and V-Sync. OptiScaler's limiter is Reflex-based (Anti-Lag 2 on Radeon), and frame generation's pacing needs the headroom; the older "3 fps below refresh" rule (237 at 240 Hz) is for limiters without Reflex. Lucent can't see the driver's V-Sync or VRR settings, so it uses one rule. The cap applies with frame generation Off too, and the Dynamic target equals it, so Dynamic aims at a number it can reach.
  - R is the refresh rate of the monitor XIV runs on (from `FFXIV.cfg`'s `MainAdapter` or window position, or its `Refreshrate` in exclusive fullscreen), falling back to the primary monitor.
  - Lucent computes it whenever it writes `OptiScaler.ini` from the baseline (first install, Reset, an update's replace rule, Repair of a missing file) and never rewrites it otherwise; a player who changes monitor uses Reset or the overlay. It replaces the hardcoded 138 and 144 that only fit a 144 Hz screen.
- **HDR** is a first-install choice, offered only when XIV's monitor supports HDR: **Off · HDR · Scene HDR**, Scene HDR tagged Experimental. The default, HDR, is the fork's original SDR expansion (`[HDR] FfxivHDR = true`, `Mode = 0`); Scene HDR is its RenoDX scene method (`Mode = 1`). With Windows HDR off, the line says how to turn it on (Win+Alt+B); OptiScaler falls back to SDR by itself.
  - Peak brightness (`PeakNits`) is computed like the frame cap, from the monitor's reported peak luminance, and the line points to the Windows HDR Calibration app for a monitor that reports it wrongly. Paper white, contrast, saturation, vibrance and highlight expansion stay as the content tunes them; players adjust them live in OptiScaler's overlay. Lucent has no brightness slider.
  - OptiScaler's HDR needs NVIDIA frame generation, XeFG or none. While HDR is on, the candidate's RTX 30 2× choice uses XeFG instead of FSR frame generation, without exposing an MFG unlock. Other tiers can add HDR provider alternatives after their own runtime and licensing checks.
  - While HDR is on, Lucent turns Windows Auto HDR off for `ffxiv_dx11.exe` only (the per-app graphics setting) and restores it when a Reset picks Off or on uninstall. RTX HDR can't be changed reliably; on NVIDIA cards the line mentions it.
  - Scene HDR's inputs for Neural Rendering, DLSS and ReShade (`NRSceneInput`, `DLSSSceneInput`, `ReShadeHighlights`) were to stay off in the content; since 2026-10-18 they ship on, like everything the maintainer has switched on (see "OptiScaler-FFXIV and the 310.9.16 runtimes"). The fork gates them on `Mode = 1`, so only Scene HDR is affected. The HDR screenshot key stays unbound. (Corrected 2026-10-23: the shipped baseline and the site guide already said on.)
- **Performance profiles** become four, each step giving up one thing:

  | Profile | Neural Rendering | Upscaling, 1080p and below | 1440p | 4K and up |
  |---|---|---|---|---|
  | **Ultra** | 2 passes | Quality | Quality | Quality |
  | **Fidelity** | 1 pass | Quality | Quality | Quality |
  | **Balanced** | 1 pass | Quality | Balanced | Balanced |
  | **Performance** | 1 pass, spatial compression, residual frame generation | Balanced | Balanced | Performance |

  - Upscaling quality is `[QualityOverrides] ForcePerfQuality`, which the fork applies live through XIV's native resolution path. XIV's own 3D resolution slider stops having an effect, and the guide says so. No DLAA: Neural Rendering stalls at DLAA with split mode. The values are content data, tuned during the Beta test; the resolution column is picked from XIV's screen, like the frame cap.
  - The default profile comes from the graphics card: the content lists the cards each profile is recommended for, and an unlisted card gets Balanced. The first-run Profile step preselects it and tags it "Recommended for your RTX 4070". Existing deployments keep their configs; for Reset, the old two-pass Fidelity is offered as Ultra, so nobody loses a pass without choosing to.
  - The content carries the four profiles in optional `performanceProfilesV2`. Lucent 0.1.x ignores the field; the legacy `performanceProfiles` field remains readable, and the schema version does not change.
- **Neural Rendering controls replace the profiles** (app 0.3.0, content 2026.10.16). The Profile step becomes Graphics and offers the settings themselves:
  - **DLSS preset**: DLAA, Ultra Quality, Quality, Balanced, Performance or Ultra Performance, which is `[QualityOverrides] ForcePerfQuality` 5, 4, 2, 1, 0 and 3 (ratios 1.0, 1.3, 1.5, 1.7, 2.0 and 3.0 in OptiScaler's own table; there is no "Super Quality"). The line under the choice shows the render resolution on the player's screen.
  - **Neural Rendering resolution**: 75%, 100% or 125% (`[DlssNr] WorkingScale`, the fraction of the frame the model works on; the frame itself is never reduced). Nothing below 75%. Cost falls with the square, so 75% is about 56% and 125% about 156%. 100% is recommended; with DLAA the step suggests 75% and offers a "Use 75%" button, but never switches by itself.
  - **Passes**: 1, 2 or 3 (`[DlssNr] Passes`); each extra pass costs about as much as the first.
  - **Spatial compression** and **residual frame generation** are switches, off by default, with their explanation under each. Residual frame generation is Experimental and needs NVIDIA frame generation, so it is offered on RTX 40 and 50 with frame generation at 2× or higher and greyed out, with the reason, otherwise.
  - **Unlock multi-frame generation** (RTX 40, Experimental) is its own switch. Without it the choices are Off and 2×; with it 3×–6× and Dynamic appear, and 2× also writes the unlock (`AdaMfgUnlock = true`). RTX 30 stays 2× only and RTX 50 has no switch.
  - The defaults follow the old recommendations: RTX 4090, 4080, 5090 and 5080 get Quality with two passes; the 4070 Ti, 5070 Ti, 3090 and 3080 Ti get Quality with one; other cards get Balanced with one. Resolution starts at 100%.
  - The controls live in the content (`neuralRenderingControls`, `mfgUnlock`), so a new upstream round stays a manifest change. A tier offers either controls or profiles, never both. The app keeps reading profiles so a rollback to 2026.10.15 still works. Reset prefills the stored picks, or the card's defaults when none are stored; existing deployments are not converted.
- **Uninstall asks what to do with the backed-up files** (app 0.3.0-beta.4). When the deployment replaced files that were in the game folder before (an old mod setup, a swapped DLSS DLL), Settings → Uninstall offers two choices: **put my earlier files back** (the default, as before) or **restore the game to vanilla**, which removes what Lucent added and leaves those files out. Vanilla keeps the readable backup copies instead of deleting them, and the notice says where they are; the choice is stored in the record so an interrupted uninstall finishes the same way. With nothing replaced there is no choice. Uninstalling Lucent from Settings → Apps keeps its single "Restore the game folder" checkbox.
- **Keys**: OptiScaler's keys are single virtual keys, without modifiers. From content 2026.10.16 the FPS overlay is on **Page Up** (`[Menu] FpsShortcutKey = 0x21`) and is taught on the Done screen; Page Down (the overlay style key) stays unbound so XIV keeps one zoom key. Neural Rendering moves to **Delete**: it sits in the same place on every keyboard, laptops and 75% boards included, XIV doesn't use it, and it pairs with Insert for OptiScaler's menu. `\` was a different key on each layout (`*` on AZERTY, `^` on QWERTZ). Before content 2026.10.16 the FPS overlay keys (`FpsShortcutKey`, `FpsCycleShortcutKey`, Page Up and Page Down by default) were unbound because they are XIV's zoom; now only `FpsCycleShortcutKey` (Page Down) stays unbound. End stays the frame generation toggle. Keys and the Done screen name keys as Windows does for the player's keyboard layout ("Suppr" on a French keyboard).
- **Check for updates**: the card's subtitle is the status line: "Checking…", "Up to date · checked 5 min ago" (the quiet check on open counts), an available update, or a yellow error. The callout at the top of Settings no longer carries the result; nobody saw it there.
- **Testing**: a Beta content version with a checklist for the RTX 4090: each multiplier, Dynamic, both HDR methods and the four profiles, each from a fresh install or Reset. Whatever fails there doesn't ship for RTX 40. RTX 20, RTX 50 and Radeon need their own tested content. No Intel-backed MFG option ships until its license clearance is resolved.

## While XIV runs

The 2026-10-14 decisions on changing settings in-game are withdrawn by the scope reset: Lucent has no setting to change after deployment.

- **Everything that writes to the game folder is blocked while XIV runs**, as in 0.1.1: Install, Repair, Reset, Update, Uninstall, Enabled and recovery. Loaded DLLs can be renamed but not replaced, and Enabled renames the entry DLLs.
- **What the tools read, and when** (checked against upstream source, 2026-10-14), kept for reference: OptiScaler reads `OptiScaler.ini` once at startup, and its overlay's *Save Settings* rewrites the whole file from memory. ReShade reads `ReShade.ini` once at startup and re-reads a preset only when it loads one; it refuses to save over a file that is newer on disk. The overlays are where players change things.

## Deployment engine

- Install steps are **declarative data in the manifest** (`copy`, `rename`, `ini_set`, `delete`); the app is a generic executor. A new upstream round ships as a manifest edit, not an app release.
- Every step is **journaled**; every overwritten or removed file is **backed up** into Lucent's data folder. Uninstall and rollback replay the journal.
- **Batched file work** (settled 2026-10-13, after installs and uninstalls took tens of seconds): consecutive copies and deletions of different paths are journaled together in one durable write, then applied at once through batch primitives the Rust side runs in parallel (`copyMany`, `hashMany`, `statMany`…). The game check runs once per batch of up to 96 files instead of before every write. Undo works the same way, newest first, in batches whose paths don't repeat. Recovery is unchanged, because a journaled step that never ran still matches its `before` hash. A 1,000-file install makes about 200 round trips instead of 15,000; `src/core/performance.test.ts` holds that line.
- Existing user setups: detect and explain, back up, then replace. User presets and shaders are carried over, never deleted.
- **Any other file at a path the content writes** (an `nvngx_dlss.dll` no signature claims, a hand-made setup's license files) is backed up and replaced the same way on a first deployment, since Scan lists it. Nothing blocks Install (settled 2026-10-13: a "move these files aside, then scan again" dead end was rejected). An update still refuses to replace such a file, since no Scan has listed it.
- **Readable backup**: a first deployment also copies every original it backs up to `%LOCALAPPDATA%\Lucent\Backups\<game folder name>\game\`, under its own path, so the player can find it. The journal restores only from its own hash-named backups, so the player can't break an uninstall by touching the copy; the copy goes once uninstall has put the files back. It costs disk space (about 700 MB for the dev machine's setup), accepted for the reassurance.
  - **Where it lives, and how the player finds it** (settled 2026-10-24, after a player had to check the site for the path): it stays in `Lucent\Backups`, and the app now shows the folder. Settings has a Backups row with Open folder (under Game folder until 1.0.2, in Storage from 1.0.3), for as long as the folder holds a copy; it opens the whole `Backups` folder, since Reset copies and other game folders' copies sit beside the install copy. Scan's "Backed up to" and the Reset review and dialog stay plain text, because they name a folder that doesn't exist yet and Open folder refuses a missing one. After a vanilla Uninstall the app is back on Scan, so the path is the one in the notice.
  - **A location inside the game folder was rejected.** The elevated Reset path is limited to `Lucent\Backups`, Open folder refuses a subfolder of a game folder, Scan, Review and the health check would have to ignore the new folder, App uninstall would stop cleaning the copies up, the copies (about 700 MB) would sit in the game folder, and players already on 1.0.0 would need a migration. What the player needed was to find the folder, not a different one.
- **Clear storage** (settled 2026-10-26, the maintainer's call; app 1.0.3): Settings has a **Storage** card with a Cache row and a Backups row, each with its size, Open folder and a **Clear…** button behind a confirmation that says what goes. Sizes are read when Settings opens and after any change. The answer ("Cleared 142 MB from the cache") shows at the top of Settings, which scrolls to it, since the buttons are lower down.
  - **Clear cache** removes every cached file: the hash-named assets and the `.tmp` downloads; a file that is not Lucent's is left, as `pruneContentCache` leaves it. Lucent already prunes the cache of what no deployment needs whenever a deployment changes, so what it holds is what Repair, a rollback or a Reset would otherwise download again. Clearing it costs a download later and the dialog says so; the game folder and Uninstall never read it.
  - **Clear backups** lists the folders of `Backups` in groups and removes the ticked ones. A live deployment's install copy and a Reset's copy start ticked, because the journal's own backups hold the same files. The originals a vanilla Uninstall left out, or those of a game folder that is gone, start unticked with "Once removed, these files can't be put back": those are the only copies. A folder no deployment record names starts unticked too, and when a record can't be read no deployment's copy is offered as redundant. **A vanilla Uninstall leans on the install copy** (found by the review before 1.0.3 shipped): it leaves the replaced originals out of the game folder, so the copy is all the player has of them, and Clear backups had removed it with the dialog's own default tick. So `uninstallDeployment` first writes any missing readable copy again from the journal's own backups, each checked against its hash (a bad one is removed), before anything changes. An original whose own journal backup is gone too (an antivirus quarantined it) can't be saved, and the Uninstall still goes ahead and says how many files have no copy: refusing would leave the player unable to uninstall for the sake of files that are already lost. A copy that fails its hash stops the Uninstall with the game folder untouched. It writes into the record's own folder, which no other game folder can have taken: `backupFolderName` keeps reserving a live record's name, cleared or not. A copy that is there is left as it is, edits included.
  - **A list that went stale** (found by the review): the groups are read when Settings opens, and another window or the player can change what a folder is before Clear is pressed (a vanilla Uninstall elsewhere, a game folder that went away, an interrupted uninstall that leaves a record applying). Clear reads the folders again under the lease and leaves any folder the list called an install or Reset copy that is no longer one, and the answer names it. A folder the player ticked knowing it was the only copy is still removed. A Reset's copy starts ticked as agreed (Lucent's own backups hold the same files) though nothing in Lucent puts them back, so the dialog says they are for the player to look at.
  - **A folder it can't list** (a junction to a drive that is gone, say) shows with no size and nothing to clear, and the other folder still shows; the card does not disappear.
  - **What it can't reach**: the journal's backups (`deployments\<id>\backups`), which Uninstall, recovery and rollback restore from. The Rust `remove_file` the code ends at deletes any path it is given, so the guard is in `storage.ts`: it lists files only under `cache` and `Backups`, refuses any listed name with `..`, an empty part or a stream or wildcard character, and checks each path stays under its folder. Tests plant such names in a lying listing and check the journal's backups after every Clear.
  - **When it refuses, and says so**: while Lucent is busy, while a change needs recovering, and while another Lucent process holds the operation lease (it takes the lease, so no other process downloads into the cache meanwhile). XIV running does not matter: neither folder is the game's.
  - **Where it is reachable**: Settings exists once there is a deployment, so after the last Uninstall the cache stays (the next install reuses it) until App uninstall removes the data folder, and the originals a vanilla Uninstall kept show in Clear backups only while another game folder still has a deployment; otherwise they are in the `Backups` folder, which the Uninstall notice names.
  - **Deliberately not done**: the journal's backups are the real pile (about 587 MB on the dev machine, growing with every update and Reset), but each is what some undo step or rollback needs. Pruning them means deciding which journal entries can still be undone and which versions can still be rolled back to, so it is a separate design (compaction), not a Clear button.
- **Config files from an existing setup** (e.g. a previous `ReShade.ini`): back up, then write Lucent's whole file. No merging: Lucent doesn't know their history. Lucent is opinionated and built for people who don't want to tinker.
- **Lucent's own config files on update** (scope reset, 2026-10-14, replacing the key-by-key three-way merge, user changes and reset keys): each content version gives each config file a **config update rule**:
  - **keep** (the default): the file is left as it is on disk.
  - **add missing keys**: keys absent on disk are written with the new baseline's value; every key already on disk keeps the player's value. For a new OptiScaler build that brings new keys.
  - **replace**: the file is backed up, then written from the new baseline and the stored first-install choices.
  - The changelog announces add missing keys and replace, and the activity log lists each file. Nothing records what Lucent last wrote.
- A whole-file replace on every update was rejected: ReShade stores the selected preset and keybinds in `ReShade.ini`, so every update would reset them.
- **Set keys on update** (settled 2026-10-24, content 2026.10.28 and app 1.0.2; the first exception to "keeps out of the configs"): a config entry may carry `setKeys`, keys an update sets in the player's file whatever their value, while every other byte stays (`docs/manifest.md`). It exists because the maintainer wanted ReShade's `SkipLoadingDisabledEffects`, `NoDebugInfo` and `ShowForceLoadEffectsButton` to reach players already installed, and the only content-only route was `replace`, which resets the selected preset and keybinds. The changelog names the keys and the journal backs the file up; a rollback restores that copy unless the player has changed the file since (ReShade rewrites `ReShade.ini` whenever a setting or preset changes), and then keeps their file.
  - **Once per key, not per update.** Recipes are copied forward, so a key is skipped when the deployed version's recipe already carries the same entry. Otherwise 2026.10.29 would set the keys again and undo a player who turned one back.
  - **`ifPath` moves a selection off a removed file.** Dropping the Alive NEXT Stable 4K preset would leave `PresetPath` pointing at nothing, and ReShade then starts with no effects. A key with `ifPath` is set only when its current value is that path, compared as a path, so the 4K selection becomes Alive NEXT Stable and every other selection is untouched. It also covers `StartupPresetPath`; `PresetShortcutPaths` (a list) is not touched.
  - **Not a new `update` value.** A fourth rule would invalidate the manifest for every older app, as with other enum values. An optional field is dropped by older apps, which then treat the file as `keep`, so the content requires 1.0.2.
  - A first install, Reset and Repair of a missing file still write the baseline, so the values also stay in the recipe's `ini_set` steps. An edited preset that a version drops is still saved as `<name> (my edits).ini`, so that one copy of a removed preset can remain.
- Shipped presets are compared by hash; a user-edited one is kept when Lucent's version is unchanged, or saved as `<name> (my edits).ini` before Lucent's changed version is written.
- User-owned and paid shaders (e.g. iMMERSE Pro: RTGI, RELIGHT, REGRADE) are never shipped and never touched.
- **Only the shaders the presets use are shipped** (settled 2026-10-13): the effects the shipped presets turn on, with their includes and textures, and the licences of the folders they come from. Another add-on naming an effect (the Shader Toggler) doesn't ship it. Players who want other effects add them themselves; Lucent leaves their shaders alone.
- Uninstalling Lucent restores the game folder to vanilla (checkbox on by default). Nothing left behind.

## Starter set (Mods)

Settled in a design grilling session on 2026-10-16 and built on 2026-10-17 (the last in-game checks are under Implementation notes). It is the one exception to "we act as the mirror for every file" (Repo and hosting): the Starter set mirrors nothing.

- **What**: a curated **Starter set** of Dalamud plugins and Penumbra mods, picked by the maintainer from the maintainer's own setup, offered to every player who wants a quick start. It stays inside "graphics mods": the plugins are the Penumbra stack and visual add-ons.
- **Shape** (replaces the "two features that reuse the journal and recipes" idea from the start of the session): a new rail section, **Mods**, with two groups, **Plugins** and **Penumbra mods**. It is independent of the DLSS 5 and ReShade flow: no Scan, no Install wizard, no Enabled, no Reset, no Uninstall of Lucent's own. Because the Starter set is seed-and-forget, it has no journal, no recipe steps and no health check, so it reuses only the manifest, the download helpers and the platform primitives. The rail needs a seventh slot; check it against the 880×600 minimum window.
- **Prerequisite**: XIVLauncher with Dalamud. Lucent never installs XIVLauncher or Dalamud. Without them the section is unavailable and says why.
- **Where the set is defined**: a `starterSet` object in `manifest.json`, at the same schema version (older apps ignore it, as with `performanceProfilesV2`), read each time the Mods section opens. It holds names, repo URLs and Heliosphere mod IDs, never binaries. It has no version, pin, skip or rollback of its own; the Versions section stays about content.
- **State comes from disk, with no nagging**: a plugin is installed when its folder exists under `%APPDATA%\XIVLauncher\installedPlugins`; a mod is installed when a folder in Penumbra's `ModDirectory` has a `meta.json` whose `Website` holds the mod's Heliosphere ID. Version never matters: Dalamud and Heliosphere update their own items. No rail dot, no drift. A removed item shows **Add** or **Get** again. The section is a menu, not a monitor.

### Plugins

- **Core set**, one **Include** switch, on by default: Penumbra, Glamourer, Weatherman, AcrylicXIV, ActionTimelineReplacement. Heliosphere belongs to the set but is not fetched (see below). **Optional extras**, each its own toggle, off by default: CharacterPanelRefined, MultiHit, Browsingway, IINACT and HaselTweaks (Browsingway and IINACT added 2026-10-18 at the maintainer's request, as extras because they serve ACT-overlay users and shouldn't install for everyone; IINACT is the parser and Browsingway shows its overlay; HaselTweaks added 2026-10-26 at the maintainer's request, as an extra because it is a broad bundle of interface tweaks, not graphics; moving any of them to the core set is changing its `group`). IINACT comes from marzent's repository and HaselTweaks from Haselnussbomber's (`MyDalamudPlugins`), each a further repo for the consent panel, which names it only when that plugin is ticked. The mod rows are link-outs, so there is nothing to force on; Penumbra is simply in the core set.
- ActionTimelineReplacement is in the core set at the maintainer's call (it is public). Its purpose is the papapachin skill mods, which are not in the set, so on its own it does nothing for a new player.
- **Fetched live, not mirrored or pinned**: Lucent reads each plugin's `repo.json`, downloads the current release (`DownloadLinkInstall`) from the author and places it at `installedPlugins\<InternalName>\<AssemblyVersion>\` with its `<InternalName>.json` manifest (`InstalledFromUrl` is `OFFICIAL` for the official repo, otherwise the repo's exact URL). Dalamud checks no hash or signature on these zips, plugins update weekly, and a mirrored copy can be refused after a Dalamud API bump, so a pinned hash would only go stale. This is the one place Lucent trusts upstream's current release. A plugin whose `DalamudApiLevel` does not match the player's Dalamud, or whose repo is down, is skipped with a visible note.
- **Third-party repos**: SeaOfStars (Penumbra, Glamourer, and the Heliosphere plugin the player installs by hand), papapachin's (ActionTimelineReplacement), marzent's (IINACT, only when ticked) and Haselnussbomber's (HaselTweaks, only when ticked) are appended to `dalamudConfig.json`'s `ThirdRepoList`, because Dalamud refuses a third-party plugin whose repo is not listed. Dalamud treats its own custom-repository warning as read as soon as any repo is enabled, so adding repos would skip it silently. Lucent therefore shows its own **consent panel** when the player clicks **Add plugins**, naming each third-party repo and its author and saying plugins have full control of the PC. Lucent never writes `ThirdRepoSpeedbumpDismissed`.
- **When Lucent writes**: only while XIV and XIVLauncher are closed (Dalamud rewrites `dalamudConfig.json` from memory while it runs, and drops keys it does not know), and only if `dalamudConfig.json` already exists, meaning Dalamud has run once. Lucent never creates it (Dalamud keeps a restoring copy in `dalamudVfs.db`). Otherwise it says "launch XIV once with Dalamud enabled".
- **Existing setups are never touched**: an installed plugin, at any version and in any state, is skipped; an existing `ThirdRepoList` entry is left exactly as it is, even disabled; only missing repos are appended. Dalamud's load check matches a third-party plugin's `InstalledFromUrl` against the enabled repos only, by exact string. So Lucent writes `InstalledFromUrl` as the exact URL already in the player's `ThirdRepoList`, and if a required repo is present but disabled it skips that repo's plugins with a visible note (it does not re-enable the repo). The edit copies the shape of the file's existing entries (Newtonsoft `TypeNameHandling.All`) and aborts if the file looks unexpected.
- **A plugin can carry a `setup` line**: what the player still does in the game (Browsingway needs the overlay URL that `/iinact` gives it; Lucent can't produce that URL and, per the rule below, never writes a plugin's settings). The report after an Add prints each placed plugin's line under **Then set up**.
- **Seed and forget**: after placement Dalamud owns the plugins (it keeps only the newest version folder, rewrites manifests and updates them). No hash check, drift, Repair or update tracking. Uninstalling Lucent leaves the plugins and repos; the player removes them in Dalamud.
- **The Heliosphere plugin is not fetched** (decided 2026-10-16). Its entry in SeaOfStars' `repo.json` points `DownloadLinkInstall` at `https://repo.heliosphere.app/latest.zip`, a Heliosphere endpoint, and Heliosphere's terms (the Third-party developers section, added 2026-08-26) bar using its services and endpoints for unofficial clients, integrations or other programs "unless given a specific written exception by Heliosphere". The terms do not mention downloading the plugin file, so a fetch may or may not be covered; Lucent does not risk it. The Plugins group shows Heliosphere as its own row: **Installed** when `installedPlugins\heliosphere-plugin` exists, otherwise an instruction to install it from `/xlplugins` once SeaOfStars is added. Lucent still appends the SeaOfStars repo, which Penumbra and Glamourer need anyway. If Heliosphere grants a written exception, fetching it can join the core set, and mod installs could be revisited with the same request.

### Penumbra mods

- **Link-out only.** The Starter set lists Hair Defined 2 (Kytsurai), AETHERIS UI AIO (djUSA.GI) and The Body SE (Tsar, **NSFW**). Each row is **Get on Heliosphere**, which opens the mod's page in the default browser, or **Installed**. Lucent never downloads a mod or touches a mod folder. The copy says Heliosphere's one-click install needs the game open with one-click paired, and otherwise the site offers a `.pmp` to import by hand.
- **Why link-out**: mods run to gigabytes, so mirroring as release assets is out. Heliosphere has no install queue (an install is a live request from the website to the running plugin), no documented API or URL scheme, and its terms ban unofficial clients or programs unless it grants a written exception. Penumbra scans `ModDirectory` only at startup and never imports a `.pmp` that was already in a watch folder; only an extracted folder works offline. If Heliosphere ever grants an exception, direct install can come back. Since Lucent does not fetch the Heliosphere plugin, a mod row's copy also says Get needs the plugin for its one-click install, and that without it the site offers a `.pmp`.
- **NSFW** items carry a neutral **NSFW** chip, set by the maintainer in the set (not read from Penumbra's tags). Yellow stays for caution and Experimental. NSFW content is allowed in the set.
- **Out of the set**: all the papa and papachin mods (paid or early-access work, 11 of the maintainer's 14). They are not listed and not linked, even to the author's ko-fi.
- **Penumbra's `ModDirectory` is read-only for Lucent**: read from `pluginConfigs\Penumbra\config\penumbra.json`, never written. Writing it would break "place and stop". When it is unset (a fresh Penumbra), mod rows say "Set Penumbra's mod folder first" and Lucent does not guess; the section's copy points to Penumbra's Settings tab.
- **Nothing is enabled**: new mods arrive disabled in every collection (read from Penumbra's source, not observed). Lucent never writes collection files, as with ReShade presets ("no preset is active").
- The set stays limited to mods the maintainer has used. It is manifest data, so adding mods needs no app release.

### Rejected

- Mirroring mods as release assets (size). Driving Heliosphere's one-click listener or `.pmp` download from Lucent (terms). Fetching the Heliosphere plugin from `repo.heliosphere.app` (the same terms). Importing a Dalamud profile or using a startup flag to auto-install (Dalamud only installs on a click or from the update path). Writing `ThirdRepoSpeedbumpDismissed`, or marking a third-party plugin `OFFICIAL` to dodge the third-party signal. Writing `penumbra.json` or collection files. Hash-pinned plugin mirrors. A journal, Repair or update tracking for plugins. A first-install tick per mod. Excluding NSFW content. A script that exports the set from the maintainer's setup (the set was derived by hand).

### Implementation notes

- **Proven in the spike (2026-10-17)**: with XIV and XIVLauncher closed, MultiHit, Character Panel Refined (both official) and ActionTimelineReplacement (third-party, its repo already listed) were placed by script, and Dalamud loaded all three on the very next start, enabled and without a warning. What it needed and what it did:
  - The manifest to place is the zip's own `<InternalName>.json` plus `InstalledFromUrl`. Lucent writes no `WorkingPluginId`, `IsThirdParty` or state flags. `InstalledFromUrl` is `OFFICIAL` (uppercase, Dalamud's constant, compared by exact string) for the official repository, and the repo's exact address otherwise.
  - Dalamud rewrites the manifest at first load (a new `WorkingPluginId`, `Disabled`, `Testing`, `SupportsProfiles`) and sets `IsThirdParty` itself. A third-party plugin loads only while its repo is in `ThirdRepoList`.
  - A plugin in no profile is added to the default profile **enabled**, so a plugin arrives switched on. "Nothing is enabled" is a rule for mods only.
  - A plugin that was removed and added again leaves two default-profile entries, the old ID and the new one. It looked harmless.
- **Checked without the game, on the real thing** (2026-10-17): all nine fetchable plugins, including Penumbra and Glamourer (Browsingway and IINACT added on 2026-10-18), download from their real links with Lucent's user agent, unpack with the real Rust extractor, and pass `assertGamePath` on every entry (`docs/qa/starter-set-plan.md`). So a large plugin is no longer a question.
- **Still to try in the game**, in one run (`docs/qa/starter-set-plan.md`): remove ActionTimelineReplacement and its repo through Dalamud, then Add it from Lucent's real window. That covers Lucent writing the repo entry itself, the entry surviving Dalamud's own save, and adding a plugin the player removed. A clean first install is optional, since the spike was a reinstall. A repo that is disabled or an address that doesn't match being refused is Dalamud's behaviour, and Lucent never creates that state.
- **Decided while building** (2026-10-17, unattended, so the maintainer can overrule any of them):
  - An invalid `starterSet` is validated apart from the rest of the manifest, so a typo in it can't take DLSS deployments down: the set is left out, the reason is kept in `starterSetError`, Mods says it is unavailable and the activity log names the mistake. The publish tool refuses to rewrite such a manifest, which would delete the set, and a test validates the repository's own set.
  - Dalamud's config is edited by splicing text into `ThirdRepoList`, never by parsing and rewriting it: a rewrite would reorder numeric keys and round large numbers. The entry's type name is copied from the file (its real namespace is `Dalamud.Configuration.ThirdPartyRepoSettings`), BOM, line endings and indentation are kept, and the result is read back and compared before it is written.
  - XIV and XIVLauncher are checked again after the downloads, just before Dalamud's config is written, and again before each plugin is copied in. Dalamud's repo list is read again at that point (2026-10-23), so a repo the player removed or switched off meanwhile is neither written for nor placed from. Nothing in Dalamud's folders is touched until every download is unpacked and checked.
  - Everything from a repo that ends up in a path is validated: the plugin's `InternalName` must match the set's exactly, its version must be a Dalamud version (`1.2.3.4`), the version folder is named after the plugin's own manifest, and every unpacked path is checked by the game-folder path rules on top of the Rust extractor's own. Nothing is ever fetched from a `heliosphere.app` address, whatever the repo says.
  - A plugin built for another Dalamud API level than the player's newest Dalamud build, or from a repo that can't be read, is skipped with its reason in a report card; the others carry on. A partial copy is removed.
  - The Add button needs XIV closed (the game check polls every second); XIVLauncher is checked when Add runs, since Dalamud runs inside the game, not the launcher.
- New Rust primitives: zip extraction with a path-escape check, and the roaming AppData path (`%APPDATA%\XIVLauncher` is already read by `xivLauncher.ts`).
- The manifest validator requires HTTPS repo URLs, a unique `InternalName` per plugin and a 26-character Heliosphere ID.
- Credits gains the authors named in the set (Ottermandias for Penumbra and Glamourer, the Heliosphere team, and the others).
- Facts above were checked against Dalamud, Penumbra and Heliosphere sources and docs on 2026-10-16. The Penumbra source read was its `testing` branch, which may be newer than the installed 1.7.2.1.

## Updates

- **App updates**: published to GitHub Releases. **Notify only** — nothing downloads until the user clicks Update. Users can skip a version or stay on one.
- **Content updates**: notify only, pinnable, one-click rollback to either of the last two cached content versions.
- **Checking** (settled 2026-10-13): Lucent checks on open, after an update, a skip or a channel change, and when the player clicks **Settings → Check now**. No background service. A manual check reports when it can't reach GitHub; the check on open stays quiet. The result shows in the Check for updates card's status line.
- **One channel switch covers both**: Stable or Beta. Beta users get beta app versions *and* beta content versions, so beta content that needs new app features can be tested before that app version ships to stable. **Leaving Beta changes nothing deployed**: the beta content stays, and Lucent then announces only a Stable version newer than the current one (never a downgrade); a running beta app is likewise offered only a newer stable release.
- **Rollback pins** the version rolled back to and **skips** the version left behind, so Lucent stops announcing it. The next newer version is announced normally. Skipped versions can still be applied manually from the Versions section.
- Manifest carries `minAppVersion`; content that needs a newer app is only offered after the app is updated.
- Manifest can mark a content version as broken on a given game version → warning for pinned users, never forced.
- **Game patch detection**: on app open, compare `game\ffxivgame.ver` and verify installed files by hash.
- **XIVLauncher integration (optional)**: register Lucent as a XIVLauncher generic add-on. Check on game launch (notify if broken), repair on game close via the `RunOnClose` option, when the DLLs are no longer locked. The add-on list lives in `launcherConfigV3.json`. XIVLauncher is not required for anything else.

## Repo and hosting

- **Single repo** for everything. We act as the mirror for every file, including Discord-only ones (no "go download this from Discord" friction). The one exception is the Starter set (Mods), which mirrors nothing.
- **In git (`main`)**: app source, `manifest.json`, inis, presets, shaders, GitHub Pages site.
- **Releases in the same repo**:
  - `app-vX.Y.Z` → `Lucent.exe`, marked as latest, so `releases/latest/download/Lucent.exe` is the stable download link.
  - `content-YYYY.MM.DD` → binaries, published with `make_latest=false`. **One asset per file, named by its SHA-256**: small delta updates, per-tier downloads, files shared across tiers and rounds stored once.
- Git cannot hold the binaries anyway: GitHub rejects files over 100 MB (`nvngx_dlssnr.dll` is 158 MB).
- **Publish script**: turns a tested folder into hash-named assets plus manifest entries; links the GPL source tag for each OptiScaler file; refuses to publish on shader path collisions with different content, or presets referencing shaders that are not shipped.

## Trust

- The exe contains no mod DLLs; it downloads them.
- **Never** add Defender exclusions. Submit each release to Microsoft for false-positive analysis.
- A GitHub Pages site in the repo is the download page and explains the SmartScreen warning before users hit it.
- **Diagnostics**: "Copy diagnostics" (versions, tier, file hashes, Windows/driver version, last 300 lines of `OptiScaler.log`) and "Report a bug" opening a pre-filled GitHub issue. Questions go in GitHub issues too (Discussions is not enabled).
- **Credits** screen in the app and on the site: OptiScaler-FFXIV (the maintainer's OptiScaler fork, whose own README credits its lineage), AMD (FidelityFX), Intel (XeSS), ShortFuse / RenoDX (compatibility runtime), Marty McFly (iMMERSE), qUINT, SweetFX, the Alive author, ipsusu (ipsuShade). Upstream license files are deployed with their files. Courtesy heads-up to upstream authors before launch.
- Context: this community remembers GShade's 2023 malware incident; open source and zero telemetry are selling points.

## Visual direction

Settled by the look prototype on 2026-10-12: variant **D · Ember**, kept as the tag `lucent-look-prototype`. Its README holds the full design language, and the tag stays as the reference. Ember combines Rail's layout ("more polished and practical, less noisy") with Prism's idea that the crystal's light is the state. It **replaces** the earlier "dark glass, aether-blue accent" direction. The references are Crunchyroll's colours and beautifului.dev's restraint. All art is original.

- **Theme**: dark only, with no OS light/dark switching. The window is opaque (no Mica or acrylic). The crystal's glow in the rail is the only painted backdrop.
- **Colour**:
  - `#F47521` orange is the **only accent**. It marks the primary action (with black `#0b0b0c` text, because white on orange fails contrast), selection, progress, the focus ring and the healthy state.
  - `#FAB818` yellow means **caution** (drift, Experimental) and nothing else.
  - `#ff6a5f` is for Uninstall.
  - Charcoal surfaces: canvas `#141519`, rail `#0d0e11`, card `#1a1b20`, field `#212329`, ink `#f4f4f5` / `#a0a0a6` / `#6e7078`.
  - Edges are 1px light rings (box-shadow), not borders.
- **Type**: Geist for the UI and Geist Mono for paths, versions, numbers and keycaps. Both are SIL OFL 1.1 and bundled (no CDN). Body text is 13px and screen titles 20/600.
- **Spacing**: 4px grid, 32px pane padding. Radius: chip 6, control 8, card 12.
- **Icons**: Lucide (ISC), 1.75 stroke at 14–16px.
- **Buttons** (refined 2026-10-13, cleaned up 2026-10-15): one 8px corner radius shared by every button and control (buttons had drifted to 10px); cards sit a touch rounder at 12px, closer to a floating panel. Controls are 32px (40px for Launch), both on the 4px grid (34/38 were off it). A disabled primary or danger button falls back to the plain secondary surface instead of a dimmed, desaturated accent fill, which read as a muddy brown or rust. Secondary controls use a faint neutral fill; ghost actions stay quiet and Uninstall keeps its solid red fill — it is the one button that's still a solid colour block, since it's the one action that should look heavier, not lighter. Hover and press feedback apply only to available actions, with a clear keyboard focus ring.
- **Primary is an outline, not a fill** (settled 2026-10-15, replacing the solid orange gradient from 2026-10-13): transparent background, a 1px accent ring and accent-coloured text, going a shade warmer on hover and a shade deeper on press — the same ring-and-text language the rest of the app already uses for a selected option, just on a button. A solid orange block read as too heavy next to the rest of the UI's restraint; this keeps Launch XIV and Continue reading as the primary action without the weight. The launch arrow shares the same outline and opens a native popover with radio choices.
- **The site** (`site/styles.css`, settled 2026-10-15) follows the same Raycast-flat direction, since it's the first thing a visitor sees of the look: its own CTA buttons dropped the chunky "pressed 3D edge" skeuomorphism for flat pills — solid orange fill for Download, an accent-ring outline (same device as the app's primary button) for everything else. Card radius tightened from 18px to 16px to read a little less bubbly. The hero background is plain (just `--page`, no glow, gradient or pattern) — four different decorative treatments were tried (a live `blur()` over a wide layer, a fixed-size background image, a gradient sized to the whole hero box, an animated SVG of drifting wave lines) and each either broke down at real page widths or was simply more than the page needed. A matching `drop-shadow` still sits under the mock app window so it feels lifted off the page.
- **The brand mark** (`Mark` in `src/ui/Rail.tsx`, mirrored in the site's inline SVGs and `src-tauri/icons/mark.svg`, settled 2026-10-15): redrawn three times before landing. A symmetric kite split by a dead-centre cross read as a toy — "cerf-volant", not a crystal — a centred perpendicular cross is the one unmistakable signature of a kite regardless of outline. A hand-faceted, three-tone, asymmetric gem fixed that but read as busy/illustrated rather than a modern app icon (checked against Raycast's own mark, which is a single bold flat-ish shape, not a multi-facet illustration). What stuck: one clean kite silhouette, no internal lines at all, filled with a single smooth vertical gradient (`--accent-top` to `--accent`) for just a touch of depth — simple, flat, modern. ## OptiScaler-FFXIV options as setup choices (settled 2026-10-23)

The analysis is in `docs/optiscaler-options.md`: what the fork exposes, what Lucent can and cannot do with it, and every option's decision. Content 2026.10.24 and app 0.3.0-beta.10.

- **Two new first-install choices**, under HDR on the Graphics step: **UI mode** (`[HudLess] Mode`: Off, Recomposition, UI-free) and **DLSS-G preset** (`[DLSSG] RenderPreset`: Auto, A, B, C). They follow the rule of 2026-10-14: written once on install and Reset, never from Home, never read back.
- **A generic mechanism, not two special cases.** A tier declares `settingChoices` (`docs/manifest.md`): options that each write the same ini keys, offered by card and by frame-generation state, with blocks by an earlier choice or by HDR. The next option the fork grows is data, not an app change. The record keeps the resolved picks for Reset, a tier switch and the administrator relaunch.
- **Shown only where they act.** Both are DLSS-G only: RTX 40 and RTX 50 with frame generation not Off. The fork says the preset is unavailable with an external frame-generation output, and that recomposition only tags FSR and XeFG outputs, untested. Where the choice is not offered an RTX 20 or RTX 30 install writes UI mode Off (it wrote Recomposition before) and no preset. With frame generation Off the picks are hidden but still written, so turning frame generation on later in the overlay finds them.
- **Defaults: Recomposition and Auto.** Recomposition is what content has shipped since 2026.10.19 and what the fork recommends; Auto is the fork's default and leaves NVIDIA's own pairing alone.
- **Blocks follow the fork.** Preset A and C turn NVIDIA's UI recomposition off (verified by the fork in `nvngx_dlssg` 310.9.16), so they are greyed out, with the reason, while the UI mode is Recomposition; before the fork's rule that pairing made DLSS-G recreate itself, after which only about 59 of about 132 presents a second were distinct pictures. UI-free is greyed out while HDR is on: the fork's design note says its paste producer cannot start under HDR output. A pick that becomes blocked is written as the default and kept in the stored picks, so it comes back when the block goes. Lucent describes the presets by what the runtime does with them (recomposition, FG Lite) and says nothing about picture or speed, which nobody has measured.
- **`[DLSSG] UIRecomposition` stays `auto`.** The UI mode already carries the on and off the player means, and the fork documents the key as mattering only in Recomposition.
- **`[HudLess] Diagnostics` ships off** (it was on). It keeps the UI-boundary observation and the ReShade probe running even with the UI mode Off, so Off would not be off, and it writes a folder of files on every run. It was on to gather data from Beta players; the maintainer can turn it back on in the recipe's `iniOverrides`. An existing ini keeps its value.
- **Older apps.** Apps before 0.3.0-beta.10 read a manifest field by field and ignore a tier field they do not know, so content 2026.10.24 keeps `minAppVersion` at 0.3.0-beta.8 and they install the base ini (`Mode = recomposition`, no preset), which is today's behaviour. The choice keys are deliberately not in the candidate script's `chosenAtInstall`, which would have returned them to `auto` for those apps. New values for an existing enum (a frame-generation id, an HDR mode) would invalidate the manifest for every older app, which is why the automatic multiplier waits for a field of its own.
- **Choices apply to new installs and Reset only.** An update's `addMissingKeys` adds absent keys and rewrites nothing, and both keys already exist in the ini. A lighter "change without a Reset" path would need an in-place ini editor and is not built.
- **A third choice, DLSS model (content 2026.10.25, with Preset E and F added in 2026.10.26):** `[DLSS] RenderPresetOverride` and `RenderPresetForAll`, as Default, Preset J, K, L or M for every quality mode, and Preset E and F tagged Experimental after them, on every NVIDIA card with or without frame generation. The options are the ones NVIDIA's Streamline 2.14.16 notes call usable for the shipped DLL (A to D removed, E and F deprecated and offered as Experimental on the maintainer's request, G to I, N and O fall back to the default), the default stays M, and the descriptions repeat NVIDIA's. It is a content-only change: the choices mechanism needed no app release, and the keys stay out of `chosenAtInstall`, so an older app installs the base ini's M. The card is "DLSS model" so it doesn't clash with the Neural Rendering card's "DLSS preset" (the quality mode). Whether 310.9.16 honours E and F is unknown: the log line `Using App hint Preset ...` says.
- **Pass preset hints** (settled 2026-10-24, content 2026.10.28 and app 1.0.2): the fork's "Advanced preset hints (effect unverified)" become three more choices, **Pass 1, Pass 2 and Pass 3 preset hint** (`[DlssNr] Preset`, `Pass2Preset`, `Pass3Preset`), the maintainer's request so players can set them without opening OptiScaler's menu.
  - **Inside the Neural Rendering card, not cards of their own.** The choices mechanism gained two optional fields: `placement` (inside the Neural Rendering card, optionally under a shared collapsed group heading) and `minPasses` (shown only with that many passes; the pick is written either way, like frame generation Off). The group is collapsed, since the fork marks the effect unverified. It reads "Advanced Neural Rendering model hints (effect unverified)" so it can't be mistaken for the card's DLSS preset or the step's DLSS model.
  - **Options follow the fork.** Pass 1: Default, Preset 1, 2, 3 (values 0 to 3). Passes 2 and 3 add Auto (inherit pass 1, written `auto`) in front. The labels are the overlay's, so a player sees the same words in both.
  - **Defaults are the shipped values** (Preset 1, Default, Default; the base ini's `Preset = 1`, `Pass2Preset = 0`, `Pass3Preset = 0`), so a player who picks nothing gets what 2026.10.27 installs.
  - **Words:** like the DLSS model options, the descriptions say what the key sends and nothing about the picture, because the fork says the effect is unverified. No option carries the Experimental tag, which would crowd five pills in a row; the group heading carries "effect unverified" once.
  - **Left out:** `Style` and the per-pass styles (the fork's profile selector, with its own tuning), and the other per-pass model strengths. They stay in the overlay.
  - First-install choices as before: a new install and Reset setup write them; an update never does, and nothing pushes them to current players.
- **Character preview Neural Rendering** (settled 2026-10-24, content 2026.10.28 and app 1.0.2): `[FFXIV] PreviewNR` becomes a choice, **Off** or **On**, **Off by default** (the content shipped it on). It runs the Neural Rendering model on the character, equipment and glamour previews, one extra model per open preview window.
  - **Why Off: it takes a lot of video memory.** Each open preview window gets its own model instance, so the cost scales with the windows open and is paid in VRAM that XIV and the rest of the Neural Rendering stack also want. The maintainer's reason for the default is that it eats lots of VRAM while active; for a feature most players use a few seconds at a time (a glamour or equipment window), Off is the safer setting. The figures are the fork's own, not measured by Lucent (`phase3-ledger/STUDY-portrait-nr-before-sr-LOG.md` in the OptiScaler-FFXIV workspace): about **+183 MB** of video memory and 2.8 ms of GPU time per preview model at the render size (576×960, what `PreviewNRBeforeSR = true`, which ships, runs; measured in a bring-up build), and about **+739 MB** and 4.1 ms per frame when the model runs after the DLSS step (1152×1920; its log was not kept). The fork's ini adds that the model stays loaded for `PreviewNRLingerSeconds` (5 by default) after its window closes. Per the fork's ini it also needs an NVIDIA card and the DirectX 11 on 12 bridge running, so it only ever applies on the two NVIDIA tiers.
  - **Where players see the reason.** The Off and On descriptions under the control say it takes a lot of video memory for each open window, with the roughly 180 MB figure on On; the guide's `PreviewNR` row says the same.
  - It sits as a plain block inside the Neural Rendering card, listed ahead of the pass preset hints so their collapsed group stays last, and the base ini ships `PreviewNR = false` too, so the file and the choice agree.
  - **A first-install choice like the others, and existing setups are left as they are** (the maintainer's call, 2026-10-24): a new install and Reset setup write it, and an update does not, so players already installed keep the `true` the earlier content gave them. Turning it off for them would have needed `setKeys` on `OptiScaler.ini` and would have overridden anyone who switched it on on purpose; it was considered and declined. Reset setup shows the choice, Off preselected.
  - The other `[FFXIV] Preview*` keys still ship as the maintainer plays, with no choice.
- **Deferred, with the reason in `docs/optiscaler-options.md`:** the automatic multiplier, the NR model version picker, the jitter options, window mode and the character preview treatment.

## Decided unattended, 2026-10-23

Calls made during the full-app review (`docs/qa/review-2026-10-23.md`) while the maintainer was away. Each is a
judgement the maintainer can overrule; the review file lists the finding behind it.

**Starter set**
- With Penumbra's mod folder unset, a mod row shows "Set Penumbra’s mod folder first" in place of **Get on
  Heliosphere** (the section's rule read literally). The cost: if `penumbra.json` is unreadable, the link-out is
  hidden too. The group note is worded separately for Penumbra installed and absent.
- Add reads Dalamud's repository list again just before it writes (after the downloads), not only the scan taken
  when the screen opened. A plugin whose repo the player switched off meanwhile is skipped ("turned off"); one whose
  repo was removed and that the consent panel did not name is skipped with a plain reason; Lucent appends only the
  repos the panel named. Official-only Adds never read the config.
- An unreadable `dalamudConfig.json` now refuses the whole Add when a third-party plugin is involved, even if its
  repos were already listed.
- A guard that fails partway through the copy loop throws `SeedInterruptedError`, which carries what was already
  placed; the screen re-scans, shows that partial report and the error. A failure before anything is written stays a
  plain error with no report.
- A repo entry with no `IsEnabled` reads as switched off, as Dalamud's bool does.
- A `dalamudConfig.json` the player set read-only refuses an Add that has to append a repo ("…because the file is read-only"); Lucent never clears the attribute. An Add that needs no new repo, and an official-only Add, still work.
- The consent dialog returns focus to the Add plugins… button when it closes; when that button is disabled again (nothing left to add) focus goes to the Plugins group's first control rather than the page body.
- The "appeared since the scan" listing swallows only not-found (a fresh Dalamud has no `installedPlugins`); any other
  listing error skips the plugin before anything is registered for cleanup.

**Updates and publishing**
- An app update's download link must be exactly `https://github.com/arnaudcouturier/lucent/releases/download/app-v<version>/Lucent.exe` and its size at most 200 MiB; both used to come unchecked from the same API response as the hash. This narrows the threat (a rogue root certificate that can forge api.github.com can forge github.com too) rather than closing it; closing it needs a hash published outside the API response.
- The release notes on the status card are cleaned of GitHub's auto-generated markdown (headings, bullets, bold, links, "Full Changelog" lines, pull request URLs). The release workflow publishes `docs/releases/<version>.md` (the lines above its first `##` heading) when it exists and falls back to generated notes with a warning.
- A content id must be newer than the manifest's newest id and at most 7 days ahead of today (UTC); a dry run warns instead of failing. A Stable content version with a beta `minAppVersion` is refused at publish time, and `npm test` checks `manifest.json` for it; the app's own validator stays lenient, so a wrong hand edit cannot make the manifest invalid for every player.
- Credits fall back to the version cached in the deployment record when the manifest is unreachable or no longer lists it.
- The publish tool prints a warning (it does not fail) when a shader name is deployed with different bytes under different paths. `reshade.fxh` and `ffxiv_common.fxh` already are, probably on purpose.
- `prepare-fork-candidate` refuses an `--output` that holds one of its inputs, or a non-empty one without the marker file it wrote earlier.

**Other**
- An app update is refused in a window Lucent itself reopened with administrator access ("This window has administrator access, so it can’t update Lucent. Close Lucent and open it again to update."): the relaunch after an update does not carry the player's SID and folders. A player who simply runs Lucent as administrator, without a UAC relaunch, can still update.
- Scene HDR's three input switches ship on (decisions line under HDR corrected to match the baseline and the guide); this settles CFG-7.

**Network, platform and screen facts**
- Both HTTP clients follow at most 10 redirects, every hop must be https and none may be on heliosphere.app or a subdomain (lowercase, trailing dot stripped); the first URL is also refused if it is Heliosphere's but is not forced to https in Rust (the TypeScript side checks it). Downloads are capped at 1 GiB (the largest real file, the 310.9.16 runtime, is 276 MB) with a 2-hour overall deadline; a text fetch is capped at 32 MiB and waits 45 s. A refused redirect or a cap is reported as an unknown error, not a network one, so the core does not retry it. Both clients ask for gzip (the releases list is 1.96 MB plain and 124 KB gzipped).
- The removal script that deletes Lucent's folder after exit runs `cmd.exe` and `ping.exe` by their absolute System32 paths from the System32 folder with delayed expansion off, and refuses a folder name containing `!`. App uninstall also deletes the toast registration key under `HKCU\Software\Classes\AppUserModelId` (best effort).
- A refresh rate is the exact rate from the display configuration rounded to two decimals (a 240 Hz panel can read 240.02 and still gets a cap of 224), and Windows' 0 or 1 ("hardware default") means unknown, never a cap of 0. The text shows one decimal ("119.9 Hz"). A 119.88 Hz panel counts as a 120 Hz screen for the 2× default (the threshold is 119 Hz).
- When XIV's `MainAdapter` is empty and the game is windowed, the window's centre, not its top-left corner, decides which monitor it is on (invisible window borders put a snapped window's corner inside its neighbour).
- On Windows 11 24H2 and later HDR support comes from `DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2`'s HDR bit, which tells an HDR monitor from a wide-gamut SDR one; older builds keep the legacy test, so a wide-gamut SDR panel on 22H2 or 23H2 can still be offered HDR.
- The graphics card is the one DXGI ranks first for high performance (external, discrete, then integrated), falling back to the most dedicated memory; an iGPU with a large carve-out can no longer win.
- Reading a log tail looks at most 2 MiB back; a config saved as UTF-16 (a byte order mark) is decoded, and is written back as UTF-8 if the core rewrites it.
- `PeakNits` still comes from DXGI's `MaxLuminance` whatever the Windows HDR state: on the maintainer's machine it reads 1015 with HDR off, so the suspected SDR value was not reproduced. Other drivers are unverified.
- Rejected after testing: treating a file with the Windows compression reparse tag (CompactGUI, `compact /exe`) as a link. Such a file reports attributes `0x20` with no reparse bit through `symlink_metadata`, so the junction and symlink check does not touch it.

**Deployment engine**
- Uninstall decides ownership of a changed file from the path's newest journal entry. A file the player put where Lucent had vacated a path (the Disabled toggle renamed the entry file away, or an update stopped deploying a file) is theirs and is left alone; a file that changed while it was still Lucent's is still removed. An edited shipped preset stays where it is (not removed and not copied): the edit is the player's work, even though that sits against "Nothing left behind". The Uninstall notice ("It removed everything it added") can therefore overstate by one file; it does not count what was kept.
- An update that drops or renames a shipped preset the player edited saves it as `<name> (my edits).ini` before the delete, like an update that changes it. An unedited dropped preset is still deleted.
- A config that cannot be read as text (not UTF-8, or it holds a NUL) is never drift: Repair leaves it, and the `keep` and `addMissingKeys` rules keep it with a line in the activity log; `replace` still replaces it after the journal backup. A config that is locked or access-denied is still drift, and one made only of zero bytes (what a crash mid-write leaves) is damage and is rewritten. Health has no channel to say a config was left because it is not text; `core.ts` `noteHealth` would need a line for it.
- A readable backup folder name is never reused while `Backups\<name>` exists (the next free numbered name is taken), so a vanilla Uninstall's kept originals survive a later deployment.
- Reset's readable copy holds the config files plus any deployed file that no longer matches its stamp (size and modified time stand in for the hash, as in the health check), not every file the plan overwrites. Review's "Files backed up" still counts the journal's backups.
- A config new to the deployment, with nothing at its path, is written and stamped under `keep` ("simply added", as `configUpdateNotes` already says); a deployed config that went missing still stays missing for Repair.
- Removing empty folders at the end of an undo is best effort (a terminal `cd`'d into `game\OptiScaler` no longer aborts Uninstall after every file is back). A deployment record's stamps must be 64 lowercase hex characters, and Repair refuses a non-config file that the content does not ship.
- Cleaning the readable backup lists from `Backups` itself and refuses to follow a link there; a junction elsewhere in the profile path still works. Scan leaves out file names the game folder rules reject (trailing dot, reserved device name) instead of failing. Stale `.tmp*` files over an hour old in the content cache are removed when it is pruned.

**Uninstall, elevation and lifecycle**
- When App uninstall cannot remove XIVLauncher's add-ons (XIVLauncher is open), Lucent no longer exits at once: the window says what is left to do and the folder and exe go when the player closes it (Close, the title-bar X, Alt+F4 or the taskbar all finish the removal). With nothing to tell the player it exits at once, as before.
- The uninstall window names the folder of readable backup copies when it will delete them (they live in Lucent's data folder). A deployment's own copies count only when "Restore the game folder" is unticked, because restoring puts those files back.
- An elevated relaunch carries the player's AppData, Documents and Pictures as well as the data folder, so the frame cap, XIVLauncher's config and the shortcut resolve in the player's profile when the administrator account differs. Known limit: HKCU, and with it the Settings → Apps entry, is still the elevated account's.
- A resumed elevated request keeps the player's HDR pick whenever the recipe offers it, even when the elevated process sees no HDR monitor; a later Scan in that process keeps the player's SID and folders.
- An elevated Reset or tier switch keeps Lucent out of the Start menu unless the player chose to add it.
- The uninstall window re-checks once a second whether the installed Lucent is open in another process and keeps Uninstall disabled with "Lucent is open in another window. Close it first, then uninstall." (a failed check counts as not running, so it never holds the uninstall up forever).
- Repair, Reset and a headless repair write nothing when the running Lucent is older than the deployed version's `minAppVersion` (from the published manifest, or offline from the record's cached snapshot): the window says "Update Lucent first: this setup needs a newer Lucent than the one you have open.", a headless run logs it and fails. Not done, left to the maintainer: an app update run from a portable copy still replaces only that copy, not the installed one.
- After an administrator relaunch Launch XIV still starts the launcher, with a notice that the game will run as administrator (XIVLauncher and the Square Enix launcher; a Steam that already runs starts the game in its own process).
- Settings that cannot be read for a transient reason (a sharing violation) are retried; if still unreadable Lucent works with defaults but refuses to overwrite the file. A damaged file reads as defaults and stays writable.
- Copy diagnostics lists only the files that differ (with a count of those that match), adds the first-install choices, launcher and auto-repair state, redacts `X:\Users\<name>` in paths and stays under 60,000 characters (GitHub's issue body limit is 65,536); the OptiScaler log drops below 300 lines only when needed to fit.
- Reset and a tier switch refresh the versions and the pending content update, and the post-Reset health check's drift reaches Home. The "starting" state of Launch XIV lasts until the launcher has started. A refused app update (the channel changed, or the version was skipped) is a notice, not an error.

**Interface**
- The tier-switch card says what a tier switch does: Enabled stays as it is, earlier choices carry over where the new tier offers them, and the config files are backed up and written again. Review for a tier switch or Reset names the folder the current config files are backed up to.
- The webview's reload keys (F5, Ctrl+R, Ctrl+Shift+R) and its right-click menu are blocked only while the core is busy, since a reload mid-operation hands Recovery a batch the old context is still writing. When idle they stay available.
- Muted ink (`--ink-3`) went from `#93969e` to `#97999f` so muted text on a selected option clears 4.5:1 (it was 4.48). Nothing else about the palette moved.
- While the Mods section is open during setup, only Mods looks active in the rail; the current step keeps its ring but loses its row fill and `aria-current`.
- The first-run rail is 28 px shorter at window heights of 640 px and below (shorter crystal stage, tighter step spacing), so the version line is no longer flush with the window's bottom edge at 880×600. Rows stay 30 px.
- A screen change moves focus to the new screen's heading only when focus had fallen to the page body after a control held it; the heading shows no focus outline and the first Tab at launch is unchanged.
- The keycap column on Keys and Done sizes to its content (120 to 220 px) and wraps, so a rebound combination such as Ctrl + Shift + F2 no longer overlaps its action.
- Settings shows why Reset setup… and Uninstall… are disabled (XIV running, or the game folder missing) above the Danger zone, in the status card's wording.
- Log lines keep a stable identity as the 500-line tail slides, so a reader scrolled up is not carried along.

**Built from the review's candidate list (2026-10-23)**
- Versions shows every changelog line of a version, not only the first: a single line stays a paragraph and several become the same bullet list the status card uses.
- The drift card has a quiet **Show files** toggle (collapsed by default) that lists what drifted: **Missing** (gone from the game folder) and **Changed** (there, with other bytes), up to 12 per group and then "and N more". When a file is missing, a line says that can mean Windows Security moved it away and that Repair puts it back; it never mentions exclusions or turning protection off (Trust). A config that exists but is zero bytes, unreadable or locked counts as Changed. `Drift.files` keeps its contents and order, so the auto-repair notification and everything else that reads it are unchanged. The card's `role="alert"` moved to its heading and text, so opening the list does not make a screen reader read the whole card again.

- **Settings → Game folder has a Change… button** (issue #1 story 10), so a second copy of the game (a Steam copy and an XIVLauncher copy, say) can be managed without uninstalling the first. It opens the same folder picker as Scan, checks the pick the same way (`game\ffxiv_dx11.exe`), writes only the `gameFolder` setting and runs the normal Scan; it never writes to either game folder or to any deployment record, and it is refused while an operation runs or recovery is needed. A folder that has a record opens as the managed game; one without starts a fresh first-run flow (every first-run choice is put back to its initial value, so nothing from the other copy leaks in). The first-run Scan screen's own Change takes you back, and a notice says the other copy's setup stays in place. Consequences: a picked folder outranks auto-detection, so reopening Lucent lands on the copy last chosen; Lucent does not report the copy you switched away from as drifted or missing until you switch back; the XIVLauncher auto-repair add-on is one entry per Lucent install and its headless run repairs the deployment that matches XIVLauncher's own game folder, and it is registered to run as administrator when any deployed game folder needs it.

- **Open folder** (a quiet icon beside a path that names a folder that exists now): Settings → Game folder, the Logs screen (Lucent's data folder, where `lucent.log` is), and the App uninstall window's Backups line. Not on folders that do not exist yet (Reset's future backup folder, Scan's "Backed up to"). The Rust command is the boundary: it accepts only an absolute `X:\` path to an existing directory and refuses UNC and `\\?\` paths, relative paths, `.` and `..`, alternate streams, wildcards, device names, a file, a missing folder, and a final name that is a junction or symlink; it calls ShellExecute on the folder with no parameters and never opens a file or builds a command line. The core adds a second layer: it only acts on Lucent's data folder (or inside it) or a game folder Lucent knows. A change to Settings' Change… icon (a folder with a pencil) keeps it distinct from the open icon. The ShellExecute call itself cannot be exercised without a real window, so it needs a check in the real exe; a folder swapped for a junction between the check and the open is not guarded.

- **Free-disk warning on Review** (install, Reset and tier switch). When a drive lacks the space the plan needs, a caution callout says so ("This needs about 1.5 GB free on C: and there is 1.3 GB.", one line per short drive, then "If the disk fills up, Lucent stops and puts everything back."). It is a warning only: it never blocks Install or Apply and never changes the plan. The need is computed per drive because the bytes land on two places that are often different drives: Lucent's data drive needs the download bytes not already cached, plus the size of the existing files the plan replaces (twice for a first install that backs files up, for the readable copy); the game drive needs the net growth (bytes written minus bytes overwritten, so a Reset that rewrites files in place asks for almost nothing) plus the largest single file (a file is written whole before the old one is released). On one drive letter the two needs add. Each drive gets a 10% plus 64 MiB margin once, after adding. The message rounds the need up and the free space down so the two figures never look equal; a drive whose free space cannot be read gets no warning. The warning is also written to `lucent.log`. Simplifications: journal backups are counted per path (an upper bound when files are identical) and a Reset's readable copy is not counted. A content update from the status card does not show this warning; only Review does.

**Declined after the review (2026-10-23), with the reason**
- CFG-4, anchoring the GPU name patterns in `manifest.json`: only "Quadro RTX 5000" and "RTX 5000 Ada" are misclassified (into `rtx-50`); anchoring on "GeForce" would break Quadro RTX 4000 and RTX 2000 Ada, which are right today. A correct fix is a negative guard on `rtx-50` plus explicit workstation patterns, in the manifest and in a new content version. Very few players use these cards and a mistake in a tier pattern breaks matching for everyone from `main`.
- CORE-7, an elevated XIVLauncher add-on that points at a user-writable exe: inherent to XIVLauncher add-ons, and the only mitigation that keeps auto-repair working for a game under Program Files is none. Code running as the same user already controls the files Lucent trusts.
- RSF-9, scoping the Rust commands to registered roots: the Rust layer is deliberately dumb primitives and the TypeScript path rules are the boundary. The webview has no HTML sink and a `'self'` CSP, and a root registry across every command could break installs.
- UPD-4's second half, refreshing the installed exe when an update runs from a portable copy: a second self-replace in the update path for a rare case, and the first half already makes Repair refuse while the installed copy is too old.
- GAP-4, re-attaching a deployment after the game folder moved: re-keying a record moves its journal and backups, and a crash partway could strand recovery data. It needs its own design. "Find it" and a rescan still work.
- GAP-1 and GAP-2, content for Radeon and Other cards and promoting anything to Stable: publishing to players is the maintainer's.
- Candidates left out: clearing old Reset backups (a deletion flow for little gain), a warning for a conflicting mod that appears after deployment (a new status card kind with precedence rules), a "Repair first" hint on Launch (Launch during drift is deliberate), resumable downloads (hash and temp-file risk in the critical path) and a minimum NVIDIA driver notice (no verified fact to base it on).
